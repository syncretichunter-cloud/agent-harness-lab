# Agent Harness：架构与接口

## 目标

构建负责推进、约束和核验 Agent 执行的运行时 Harness；用工单助手证明它能完成具体任务。以下是工程设计和验收边界，不代表当前已经实现的模块。

Harness 核心不内置退款政策、订单表结构或客服专属状态。业务通过工具、策略、信息供给和结果验证接口接入。不为追求通用性提前制造插件市场、复杂依赖注入框架或任意流程语言。

## 职责边界

- **模型**：根据给定上下文产生文本、动作或计划候选；其声明不是任务完成证据。
- **Harness 核心**：维护任务生命周期，构造上下文，调用模型，校验/分派动作，处理观察和恢复，执行停止规则并核验结果。
- **业务适配**：订单和政策数据、教学退款工具、领域权限规则与完成断言。Harness 调用这些接口，而不是猜测业务事实。
- **执行环境**：数据库、受限工具进程、沙箱、凭据与网络边界。Harness 使用环境提供的隔离和持久能力，不凭 Prompt 代替权限。
- **模型后端与任务调度**：提供推理服务、排队和资源控制，通过适配接口接入；不是模型—工具循环本身。
- **评测与诊断**：运行时完成核验属于任务闭环；离线任务集、模型裁判和回归执行器属于开发验证工具。运行事件支持 Trace，不能把诊断推断冒充执行事实。

## 一次任务的运行路径

```text
业务入口提交任务 + 身份/策略上下文
  → Harness 加载/创建任务状态
  → 检查取消、审批与预算
  → 构造工作上下文（历史、记忆、按需证据）
  → 模型适配器返回动作/文本候选
  → 控制流选择下一步
  → 校验动作契约和权限
  → 工具执行器调用业务工具
  → 保存结构化观察与动作结果
  → 更新状态、检查点和产物
  → 完成验证器核对任务条件
  → 继续 / 等待用户或审批 / 转人工 / 完成 / 失败 / 取消
```

运行事件覆盖全程。恢复时不能盲目重放未知副作用，应先使用操作 ID 核对业务系统结果。模型生成答案不自动进入完成状态；等待人工批准也不等于失败。

## 核心契约

以下名称表达职责，不预先锁死类名、框架或数据存储。

- **任务状态**：输入任务 ID、身份/租户上下文和版本；输出当前阶段、已核验动作、待办及产物引用。持久状态与一轮 Prompt 分开。
- **模型调用**：输入工作上下文、动作 Schema、模型配置和剩余预算；输出兼容的候选结果、用量及失败类别。更换后端仍需通过 Schema/工具/任务回归。
- **上下文构造**：输入任务状态、历史、记忆与证据；输出预算内的模型输入与来源引用。缺少信息时可以补问或查询，不能编造。
- **信息供给**：输入查询、身份范围、有效期约束；输出结构化事实/证据、来源与版本。关键词、向量、数据库和实时 API 是可替换实现。
- **工具执行**：输入调用 ID、工具名、参数、身份/策略和幂等信息；输出成功、失败或未知的结构化观察及可查询副作用标识。超时不等于未执行。
- **策略与审批**：输入身份、动作参数和审批记录；输出允许、拒绝或待审批。审批绑定具体参数，模型不能自行签发权限。
- **完成核验**：输入任务条件、观察、产物和业务状态；输出已完成、需继续、待人处理或失败，并附证据。语义裁判不能代替可确定的业务断言。
- **预算与停止**：输入累计调用、用量、时间和取消信号；输出剩余额度与继续/停止理由。停止后不能再发起新的未授权副作用。
- **运行事件**：输入模型、工具、状态和错误事件；输出关联 ID、版本、脱敏记录与指标。记录足以诊断但不泄露密钥或个人信息。

## 代码组织与依赖

目标职责按以下目录组织，在对应章节实现并验证后加入；此处不展示尚不存在的运行命令。

```text
src/
├── harness/                 # 循环、状态、上下文、工具契约、策略接口、核验、事件
├── integrations/            # 模型、MCP、持久化等具体适配
└── examples/support/        # 工单入口、政策、订单、业务策略和教学退款工具
tests/                       # 核心契约、业务集成、恢复与安全测试
evals/                       # 任务数据、执行器、对照与回归
scripts/                     # 初始化、启动、评测和复现
```

依赖方向：工单示例和具体适配实现依赖 Harness 接口；Harness 核心不导入工单模块或某家模型 SDK。HTTP/CLI 入口属于应用接入，不与核心执行机制混成一个大函数。简单实现足够时不为了目录齐全制造空模块。

## 如何验证 Harness 本身的作用

- 尽可能固定模型版本、任务、数据、采样配置及总预算，只改变待验证机制。
- 分别记录任务结果、安全副作用、调用次数、延迟、用量和人工介入；更多调用换来的改善需要明确成本。
- 必要的非固定因素单独列出；随机性需要重复与不确定性说明。
- 对模型服务或量化的扩展实验，固定 Harness，避免将模型/后端变化误归因为 Harness 改造。
- 最终用小型非工单任务复用核心接口，检查业务适配是否真正独立；不以此宣称通用框架已经成熟。
